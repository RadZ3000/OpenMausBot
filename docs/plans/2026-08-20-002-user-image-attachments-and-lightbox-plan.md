# feat: User image attachments across engines, plus an image lightbox

## Summary

A user can already drop a file on the window, but only its **path** ever reaches the
model: `composeMessage` folds every attachment into one string as
`<attached-file path="…" />` ([src/lib/composer-attachments.ts:143-153](src/lib/composer-attachments.ts#L143-L153)),
and `POST /api/bots/:id/messages` accepts nothing but `{ text }`
([server/index.ts:3104-3121](server/index.ts#L3104-L3121)). Three consequences:

1. A screenshot on the clipboard cannot be sent at all — a drag with no disk path is
   rejected outright ([src/lib/composer-attachments.ts:97-104](src/lib/composer-attachments.ts#L97-L104)).
2. No engine ever receives pixels. A vision model is handed a file path and has to
   guess whether it may open it.
3. Nothing the user attaches appears in their own transcript bubble.

This plan makes attachments first-class on the wire, delivers real image content to every
engine in that engine's own protocol shape, and adds a shared lightbox so any image in the
transcript — attached by the user, generated by the bot, or captured from its desktop —
opens full-screen.

## Problem Frame

**Root cause:** there is no attachment concept below the composer. `SendTurnInput` carries
`text: string` and nothing else ([server/contracts.ts:140-176](server/contracts.ts#L140-L176)),
so the string is the only channel and flattening happens in the client before the harness
can make a per-engine decision.

**The non-obvious half — protocols disagree about what an image *is*.** Verified against
the real binaries and the spec, not assumed:

- **Codex** takes a **file path**, not bytes: `{ "type": "localImage", "path": "…" }` inside
  `turn/start`'s `input[]`. Probed live against the installed codex-cli — a PNG of three
  color bands came back described as "Purple / Orange / Green", so the pixels genuinely
  reach the model.
- **ACP** takes **base64** (`{ type: "image", mimeType, data }`) and the spec is explicit
  that "Clients **MUST** restrict types of content according to the Prompt Capabilities
  established during initialization". Agents advertise
  `agentCapabilities.promptCapabilities.image` at `initialize`. `core.ts` currently reads
  only `authMethods` from that response ([server/drivers/acp/core.ts:514-519](server/drivers/acp/core.ts#L514-L519)).
  Every ACP agent **MUST** support `resource_link`, which gives a lossless fallback.
- **Claude Code** takes Anthropic content blocks on stdin, where `content` may be an array
  rather than the plain string sent today ([server/drivers/claude.ts:656-658](server/drivers/claude.ts#L656-L658)).
- **grok** is HTTP and takes OpenAI multimodal `image_url` parts.
- **boxAgent** and **antigravity** take a single prompt string and cannot carry an image.

So "send the image to the model" is six different payloads, and one of them (ACP) is only
legal if the agent said so. A driver that guesses wrong is exactly the failure mode that
produced the MCP-approval bug: silent rejection.

**Scope:** an upload endpoint and on-disk attachment store; `attachments` on the message
and on `SendTurnInput`; per-driver rendering in five driver files; composer paste/pick/drop
with thumbnails; a user-attachment bubble; a shared lightbox; tests.

## Key Technical Decisions

**KTD1 — Attachments live on disk and are referenced by path; base64 never touches the
`Message`.** Every message the store writes is broadcast to all SSE clients in full
([server/index.ts:266-300](server/index.ts#L266-L300)) and serialized into SQLite's `json`
column ([server/message-db.ts:130-154](server/message-db.ts#L130-L154)). Inlining a 3 MB
screenshot would push it down both paths, to every connected client including a phone on
cellular. The message therefore carries only `{ id, name, mime, size, path }` and pixels
are fetched on demand from a new route.

This deliberately diverges from the generated-image flow, which stores `png` inline and is
never pruned. That is a known wart — `pruneScreenFrames` covers `kind: "screen"` only
([server/store.ts:668-687](server/store.ts#L668-L687)) — and inbound user uploads are
higher-volume and arbitrary-size, so they should not repeat it. Rejected: reusing `png` on
the message for symmetry; it trades a real scaling problem for cosmetic consistency.

**KTD2 — The harness passes attachments *structurally*; each driver renders them.** The
alternative is to keep flattening in `composeMessage`, which forces one lowest-common
shape for all twelve drivers and permanently prevents vision. `SendTurnInput` gains
`attachments?: TurnAttachment[]`; a shared `attachmentsAsText()` helper gives the drivers
that cannot do better a fallback identical to today's behavior, so no engine regresses.

**KTD3 — Each driver emits its own verified shape, and ACP gates on the live
advertisement.** `core.ts` starts capturing `promptCapabilities` from the `initialize`
result it already awaits, and sends an `image` block only when the agent advertised one,
falling back to `resource_link` (a baseline MUST for every agent) otherwise. Nothing is
advertised that a driver cannot deliver. Rejected: sending image blocks unconditionally
and letting agents that dislike them error — that is the guess-and-hope pattern that
already cost us a bug, and it fails the turn rather than degrading.

**KTD4 — Non-image files keep today's path-reference behavior.** A file's path is the
right payload for an agent that has a read tool; base64-ing a 40 MB archive into a prompt
is not. Only images become content blocks. This keeps the diff honest about what
"file uploads" can mean for a coding agent.

**KTD5 — One lightbox component serves all three image surfaces.** `ScreenFrame`,
`GeneratedImage` and the new attachment thumbnail each render an `<img>` today with no
affordance beyond its inline size ([src/components/ChatView.tsx:487-507](src/components/ChatView.tsx#L487-L507)).
A single overlay keyed by source avoids three divergent viewers.

## Phases

### Phase 1 — Lightbox (self-contained, no protocol risk)

| File | Change |
| --- | --- |

### Phase 2 — Attachment storage and the upload endpoint

| File | Change |
| --- | --- |
| `server/attachments.ts` *(new)* | Write bytes under `DATA_DIR/attachments/<threadId>/`, sanitize the filename, sniff and validate the MIME from magic bytes rather than trusting the client, enforce a per-file cap. Resolve a stored attachment back to a path for reading. |
| `server/index.ts` | `POST /api/threads/:threadId/attachments` (uses `MAX_IMAGE_BODY_BYTES`, not the 1 MB default); `GET /api/threads/:threadId/attachments/:id` to serve bytes with immutable caching, mirroring the existing message-image route. |
| `server/attachments.test.ts` *(new)* | Traversal attempts in the filename, MIME sniffing, oversize rejection, round-trip read. |

### Phase 3 — Attachments on the message and through the turn

| File | Change |
| --- | --- |
| `server/store.ts` | `Message.attachments?: Attachment[]`. Kind stays `"text"`, so no client that switches on `kind` breaks — including the iOS `Kind` enum, which would otherwise decode a new kind as `.unknown`. |
| `server/contracts.ts` | `SendTurnInput.attachments?: TurnAttachment[]`; `ProviderAdapter.capabilities.imageInput?: boolean`. |
| `server/index.ts` | Both message POST routes accept and validate `attachments`; `startTurn` puts them on the message and forwards them to `sendTurn`. |
| `server/turn-attachments.ts` *(new)* | `attachmentsAsText()` — the shared fallback rendering, byte-identical to today's `<attached-file …/>`. |
| `server/harness/registry.ts` | Surface `imageInput` on `InstanceInfo.capabilities`. |

### Phase 4 — Per-driver delivery

| File | Change |
| --- | --- |
| `server/drivers/codex.ts` | Append `{ type: "localImage", path }` items to `turn/start` `input[]`. `imageInput: true`. |
| `server/drivers/claude.ts` | Send `content` as a block array with base64 image blocks when images are present, string otherwise. `imageInput: true`. |
| `server/drivers/acp/core.ts` | Capture `promptCapabilities` at `initialize`; append `image` blocks when advertised, else `resource_link`. `imageInput: true`. |
| `server/drivers/grok.ts` | Multimodal `content` parts with `image_url` data URLs. `imageInput: true`. |
| `server/drivers/boxagent.ts`, `antigravity.ts` | Text fallback via `attachmentsAsText()`. `imageInput` stays false. |
| Driver tests | One case per driver asserting the emitted payload shape; ACP gets both branches (advertised and not). |

## Verification

- `pnpm typecheck`, full `pnpm test`, and lint parity against a clean `HEAD` worktree —
  the same bar the image-generation work was held to.
- Live end-to-end against Codex with the banded-PNG probe, asserting the model names the
  bands back. That is the only check that proves pixels arrived rather than a path.
- Manual: paste a screenshot, drop a PNG, pick via the button; confirm the bubble
  thumbnail, the lightbox, and the model's reply.

## Risks

- **Claude and the ACP engines cannot be probed here** — only codex and claude are
  installed, and claude is not logged in. Their shapes come from the published protocol
  rather than observation, so ACP is gated on the agent's own advertisement and Claude
  keeps the plain-string path whenever no image is attached, confining any error to turns
  that actually carry one.
- **Disk growth.** Attachments are never garbage-collected by this plan; thread deletion
  should remove the directory, and anything beyond that is follow-up work.
